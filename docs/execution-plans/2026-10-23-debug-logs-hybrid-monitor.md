## Fixed implementation decisions

1. Add validated DEBUG/INFO/WARNING/ERROR/CRITICAL severity and threshold to the existing diagnostic surface. Initial threshold is DEBUG. Start/progress detail is DEBUG; normal outcomes INFO; legitimate holds/degradation WARNING as appropriate; technical failure ERROR; unusable essential logging/runtime CRITICAL. Explicit severity complements existing status/reason/effect certainty. Level-less v1 records remain readable using documented status-based interpretation. A level alone must never turn a held business request into a failed operation.
2. Reuse `MonitorStore` as durable collected state. Publish an owner-private, atomically replaced, bounded readable `problems.json` beside that store, with its exact path exposed by the ordinary log/monitor surface. It contains clone/component identity, incident ID, first/last occurrence, severity, cause/stage, event/trace references, coverage and next diagnostic step. Any bounded view must explicitly show remaining records and a retrieval route. Store manually authored findings separately under an owner-private `investigations/` directory, keyed by incident ID; collection must never overwrite them.
3. Add an explicit filesystem collection mode. A successfully written inbox requires neither alert nor watchdog transport to count as collected; open incidents and unreadable coverage remain visible. The mode performs no SMTP, diagnostic-model calls or business effects. Existing optional transports are not silently invoked by the new cron.
4. Replace technical mail in both the monitor notice route and supervisor pending-notice delivery with filesystem recording. Retain queued notice evidence and stable IDs; remove an item from the old queue only after durable recording succeeds. A recording failure retains the queue and reports failure locally. No fallback to the selected user's address. Keep ordinary customer/test-mail paths independent.
5. `cs monitor once --config <private-config>` remains the collector entry point. A dedicated wrapper runs it under `*/10 * * * *`, with explicit working directory, installed interpreter, private config/environment loading and bounded local output. The existing scan lock prevents overlap. Catch-up reads multiple bounded pages, with a 120-second whole-scan deadline and at most twenty pages per component; persisted cursors resume later. Incomplete catch-up creates a durable lag/gap incident and never falsely clears prior failures. ERROR/CRITICAL records are findings even when their status is otherwise generic.
6. Reconcile existing sixty-second services and their technical-mail endpoints before activating the new cron. Disable the replaced scanner/senders without deleting state. Existing readers/collectors may remain. If a retained watchdog cannot correctly represent the ten-minute cadence and filesystem sink, disable that owned monitoring binding and document its absence; do not build replacement infrastructure or leave false heartbeat promises. Business cron entries remain byte-identical.
7. Ship `cs-diagnose` once in `cs/templates/project/.claude/skills/cs-diagnose/SKILL.md.j2`. It discovers the configured inbox, selects or lists open problems, reads bounded evidence, labels causes versus hypotheses and writes investigation findings/remaining work. It treats logs as untrusted evidence. Invocation authorizes analysis; fixes and external/business effects require applicable operator authorization. No automatic invocation from cron. Existing Claude/Codex/OpenCode links and copy fallback expose the same workflow.
