### 3. Cron control knob

The knob is **`CS_PAUSE`**, not `CS_STOP` (confirmed: zero hits for
`CS_STOP` anywhere in `mrcall-cs/` or `cs-kernel/`). It is a **file**, not an
env var: `<state_dir>/CS_PAUSE` (i.e. `~/.mrcall-cs/CS_PAUSE` for this
clone). Implementation is entirely kernel-side:
- `cs/config.py` exposes it as a `Settings` property (`state_dir /
  "CS_PAUSE"`).
- `cs/campaign.py::_pause_active()` is the actual check — "Global
  kill-switch: `<state_dir>/CS_PAUSE` present → do nothing" — consulted by
  every campaign send path (`send_reminder`, `send_sms`, the confirm-check
  path), each returning `{"ok": False, "blocked": "CS_PAUSE active"}` when
  the file exists.
- `cs/sms.py` raises `SmsError("CS_PAUSE active — global kill-switch")` on
  the same check.
- The cron wrapper (`bin/cs_operator_cron.sh`) checks it too before invoking
  the operator at all.
- `cs cron install` prints the pause hint on install: `Pause: touch
  ~/.<slug>-cs/CS_PAUSE`. Resuming is deleting that file (its own stored
  content says as much — see below).

**Live state, checked directly, 2026-08-22:**
- `ls ~/.mrcall-cs/CS_PAUSE` → **No such file or directory. The file does not
  currently exist.**
- `.venv/bin/cs cron status` (run from the mrcall-cs repo) → `Not installed.
  Run: cs cron install` — confirming the crontab has no `# cs-cron:mrcall-cs`
  tagged entry at all right now.
- `crontab -l` confirms this independently: the only mrcall-cs lines present
  are the two batch-2 entries (`giada_cron.sh`, `migrator_cron.sh`), both
  date-scoped to day-of-month 24-31 of month 7 (July) — dormant until July

## `founder_sweep` — full analysis (2026-08-22, third task)

Commissioned on the premise that `founder_sweep` "is defined in cs-kernel
manifests but never used." **The premise is wrong.** The feature is wired
end to end and ran successfully in production three hours before this
analysis. It must not be removed. It does, however, carry a live permission
defect that makes it fail intermittently, and a latent security-shaped gap
of the same shape.

### 1. What it is

A per-clone, strictly **read-only** surface onto a SECOND mailbox, alongside
the operator's own. Two independent consumers:

**Consumer A — cron tick step 4b (the main one).** When
`[engine.founder_sweep] enabled = true`, `cs init`/`cs update` render an
extra section into the clone's `cs-operator` skill
(`cs/templates/project/.claude/skills/cs-operator/SKILL.md.j2:102-125`,
`{% if founder_sweep_enabled %}`). Each tick the operator runs:

```
.venv/bin/python -m cs --account <founder> tasks
.venv/bin/python -m cs --account <founder> ask "List the mail to <founder> from the last 4 days that still looks unanswered by a human. …List only, no drafts."
```

and folds one line into the report. The template's own stated rationale:
that mailbox's engine profile has no trained voice / `USER_NOTES`, so
composing there would be ungrounded, and by design the autonomous
draft/triage loop stays on the support mailbox only. It is the ONE step
that reads a mailbox other than the operator's own, and it drafts nothing,
sends nothing, marks nothing, writes no memory.

**Consumer B — `cs project new`.** `cs/project_memory.py:149` computes
`owner_account = settings.founder_sweep_account or settings.email_address`
and feeds it to `templates/project_memory/README.md.j2:45-50`, so a new
project dossier tells the next session which mailbox to search. The comment

The mechanism itself is entirely generic: the `--account` flag

(~line 674) was built *for* this feature. `founder_sweep` is only the
on/off + which-account pair; nothing about it is company-coded in `cs/`.

### 3. Should it be removed — no. Fix two defects instead.

Removing it breaks 124-cs's live operator and silently degrades
`cs project new` on any clone whose relationships live in a founder inbox.
It is a real, rule-of-two-eligible feature (one clone uses it today; the
other is one manifest flip away — `mrcall-cs` already registers
`mario.alemi@mrcall.ai` in `CS_ACCOUNTS` with a real uid).

**Defect A — live, and the direct cause of observed failures.** The kernel's
permission template `cs/templates/project/.claude/settings.json.j2` contains
**zero** `--account` rules; every allow entry puts the verb immediately
after `cs` (`Bash(.venv/bin/python -m cs tasks:*)`, `…cs ask:*`, …).
Permission rules match command TEXT, so the sweep's own documented
`cs --account <addr> tasks` matches **nothing** in the allow list. Observed
consequence in the live log:

- `2026-08-21T18:00Z` → `mario.alemi@cafe124.it: impossibile controllare —
  sistema permessi blocca le query su account alternati`
- `2026-08-22T06:00Z` → `mario.alemi@cafe124.it: non verificato (approval
  required)`

This is precisely the failure mode the charter's invariant 4 and the cron
wrapper's own comment warn about ("a missing spelling is a hole"), applied
to the allow side, which nothing gates. Fix: emit `--account`-carrying
spellings for the read-only verbs (`tasks`, `ask`, `thread`, `whoami`) when
`founder_sweep_enabled`, and extend the `tests/run.sh` enumeration gate to
cover the allow side, not only the deny side.

**Defect B — latent, security-shaped, same root cause.** The cron wrapper's
`--disallowed-tools` re-deny set has the identical gap:
`cs --account X chat` does not match `Bash(cs chat:*)`. Today this is not
exploitable, because the allow side is equally narrow — the `--account`
form matches nothing at all and so always falls through to a prompt (which
headless denies). But the wrapper's own comment says the deny block exists
specifically to survive a human relaxing `settings.json` to send from the
REPL. A broad relaxation (e.g. `Bash(.venv/bin/python -m cs:*)`) would open
the `--account`-prefixed send surfaces with **no re-deny behind them**.
Whichever way Defect A is fixed, Defect B should be closed in the same
change.

### Secondary observation, out of scope, pre-existing

`SKILL.md.j2`'s report block is hardcoded Italian ("Print one compact

Pre-existing and unrelated to `founder_sweep`; noted, not acted on.
