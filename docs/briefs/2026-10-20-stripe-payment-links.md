# Explicit Stripe Payment Links

The operator wants to create a fixed EUR payment link (example EUR35) from the current interactive Stripe workflow. Existing integration intentionally supports reads only. Extend the shared engine capability and cs-kernel workflow; do not bypass the skill with direct provider calls from a clone.

Scope: a typed engine RPC for creation of a one-time, fixed-amount EUR Payment Link and its prerequisite Stripe Price/Product; kernel convenience CLI and canonical cs-stripe procedure for all three hosts. Existing Desktop key storage and connection UI remain usable. Require only the additional Stripe Payment Links, Prices and Products write permissions for this operation; leave the six read connection probes unchanged. Return explicit actionable permission failures.

Inputs are exact integer EUR cents, a human-provided item label and a stable request identifier. Creation must require the human's explicit request; no extra authorization checkbox or repeated consent ceremony. A Payment Link is reusable for one-time purchases unless Stripe restricts it; it does not itself charge a customer. No recurring price, refund, subscription mutation, arbitrary endpoint, contact targeting or send is added. Unknown/ambiguous item or amount must be clarified before an actual external creation.

Preserve verified owner/profile/installation/company/account/mode/session/generation binding before each provider write and after responses. Restrict provider POSTs to /v1/prices and /v1/payment_links with server-constructed fields and deterministic per-stage Stripe idempotency keys. Persist private encrypted operation state; same request+payload reuses prior work, conflicting payload refuses, and an unresolved retry beyond the provider idempotency window refuses rather than risking a duplicate. Failures after a successful Price creation retain resumable state. Never expose or log keys/provider response bodies.

Scheduled/headless use is denied by both typed and raw CLI dispatch plus all six launcher spellings in the cron deny surface. Canonical Claude permissions ask for the explicit interactive mutation (overriding the broad RPC allow); they must not unconditionally deny interactive use. These textual host rules are not a universal sandbox for other hosts. No existing send/auth/email/model behavior is changed. Mutation permission changes need their own applicable checks; do not claim the existing read-only public release or unrelated hosted case certifies this new capability.

Acceptance: deterministic real RPC/HTTP construction tests cover EUR3500, invalid inputs, account/mode/session/connection changes, missing write permissions, timeout/partial recovery, stable retries and duplicate prevention; existing read tests pass. CLI/three-host rendered distribution and scheduled refusal are verified. Source delivery is committed/reviewed; installed activation is coordinated with current runtime owner and preserves the actual selected candidate, configuration and all unrelated files. No restart/adoption while an owner hold exists. No paid model trial or real charge is needed. Actual provider creation additionally requires an eligible connected key and explicit item details.

Rollback: restore only captured owned source/skill/permission files and exact service source binding if activated. Existing credentials and reads remain intact. Provider objects already created are reported with IDs; never silently recreate or delete them. Public release, broad operational acceptance and automatic customer sending remain separate.
