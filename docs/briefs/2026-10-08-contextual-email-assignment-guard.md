# Assignment holds at every contextual email write

Date: 2026-10-08. Substantial local development; release and live activation excluded.

## Intent

Prevent the generic chat / MrCall send-mode route from drafting or sending a contextual email reply while the exact thread is assigned to a person, awaiting verification, already acknowledged closed, conflicting, or unavailable. The engine must enforce this at its actual draft write and outbound transport boundary, including drafts created before an assignment. Tool approval is permission to perform a send, not permission to override company assignment authority.

This deliberately changes the previous opt-in contract: the existing assignment draft test explicitly permits an unscoped Desktop reply draft on an assigned thread. Preserve genuinely source-free standalone composition and unrelated threads, rather than imposing sender-wide ownership. Do not infer reply intent or human presence from prose, email domain, a TTY, a caller boolean, or a generic chat approval.

## Current evidence and affected owners

Desktop engine `services/task_assignment_draft_policy.py:guard` returns immediately when its ContextVar is absent. `storage/storage.py:Storage.create_draft` uses that decorator, so generic chat bypasses the hold. `rpc/methods.py:chat_send` installs scope only for optional assignment_thread_key; `services/chat_service.py:process_message` uses special draft-only routing solely when that scope exists. Kernel `cs/rpc.py:chat` and `cs/cli.py:cmd_draft_reply` negotiate that limited policy; generic chat and exact-draft send do not.

Actual outbound paths requiring authoritative coverage: `tools/gmail_tools.py:SendDraftTool.execute`; `services/command_handlers.py:/email send`; `services/solve_tools.py:_send_email`; `email/imap_client.py:send/send_message`; and legacy task-orchestrator OAuth send branches in `agents/task_orchestrator_agent.py`. The latter OAuth imports currently refer to absent gmail/outlook modules: preserve that limitation and guard their entry points, without claiming working OAuth provider acceptance or inventing transports. Draft updates must not erase/change established source binding. All create_draft callers share the storage boundary.

Reuse the existing assignment identity/trust admission, exact RFC parsing, owner-scoped mail source resolver, complete projection, company writer lock and latest-row CAS. Shared records remain metadata-only; private ordinary and Qonto tasks stay private.

## Assignment applicability and durable enrollment

Add a single company-bound enrollment record, stored beside ProjectSpace under the existing company database binding. States are `never-enabled`, `managed`, and `legacy-unknown`; schema/version and exact immutable space ID are mandatory. Managed is a monotonic latch, not a mutable preference. A complete readable `never-enabled` record establishes that assignments have not been enabled; absence of trust, an empty assignment ledger or lack of request scope never establishes that fact.

The installation path must inspect and retain pre-install schema evidence before `memory.store._ensure_memory_tables` creates missing tables, under its existing migration file lock. Fresh company creation initializes `never-enabled` atomically with its new ProjectSpace. A genuine pre-assignment upgrade (none of the three assignment tables existed before installation, with complete successful schema inspection) may initialize `never-enabled`. A partial assignment schema, failed inspection, missing/mismatched enrollment, or ambiguous legacy store with previously present assignment tables cannot be classified as never-enabled automatically. Existing valid root-owned trust or any task/event/receipt history makes the company `managed`; history without valid trust remains managed and blocked. Existing assignment-capable empty stores with no marker and unavailable trust become `legacy-unknown`, since they are indistinguishable from empty companies whose trust was revoked. Migration is idempotent and preserves the original classification evidence; a restart after additive table installation must not reclassify a previously ambiguous store.

Ordinary fresh local Desktop profiles and provably pre-assignment upgrades therefore keep their existing contextual reply behavior without `/etc` files, privileged configuration or an administrator. They still require readable current company binding/enrollment. Ambiguous legacy profiles fail closed with a specific remediation diagnostic; do not claim automatic compatibility for them. Their classification is an explicit one-time migration obligation for current assignment-capable local Desktop stores. A documented offline maintenance procedure may classify legacy-unknown as never-enabled only when the trusted filesystem/data owner independently attests that this company never had assignment authority; successful empty-table/trust inspection alone is insufficient. This has the same authority and trust limits as existing direct database writers: local company-data owner for a genuinely local store; independent privileged host operator for hosted stores. It is not an RPC, ordinary chat approval, self-approved human flag, or a tenant-callable hosted command. The procedure locks the exact company store, verifies immutable space ID, complete schemas, no task/event/receipt history and no valid or malformed/unavailable trust authority, preserves an audit record of the explicit trusted classification, and cannot run against managed enrollment or erase any history. A host operator can instead enroll an ambiguous company as managed by the normal privileged procedure. The guide must clearly disclose that classification rests on this independently trusted historical knowledge, not proof derived from missing files. No API or tenant command can reset managed enrollment, clear its audit, or perform this classification. Source migration/classification completes before contextual effects are admitted; actual six hosted engines already have valid trust and classify managed without a new human decision.

Enablement is a root-owned standalone provisioning operation, not an RPC. It acquires the same company writer lock used for final effect admission and durably latches `managed` BEFORE installing or changing public trust. If trust installation fails, the retained managed record causes refusal rather than downgrade. The operation verifies the actual store/space and preserves existing trust/key permission rules. Existing direct trust-file installation procedures are replaced in the operational guide by this ordered enrollment procedure. Existing already-trusted deployments are migrated to managed before serving; no live migration is executed by this development task. Missing, revoked, unreadable or malformed trust on a managed company refuses all contextual reply effects even when its assignment tables are empty. Trust removal never clears enrollment. Reads may detect an unexpected valid trust file and latch managed under the company lock; existing assignment APIs must likewise refuse a never-enabled or unknown store unless the trusted provisioning/migration has enrolled it, rather than activating authority through a tenant call.

Final never-enabled admission rechecks enrollment and any trusted authority signals while holding the company writer lock through the private write or bounded irreversible transport handoff. Privileged enrollment uses that lock, so either the unmanaged send completes before enrollment takes effect or enrollment wins and the send is re-evaluated as managed. Arbitrary root/filesystem tampering outside the required provisioning procedure remains the existing trusted-writer boundary, not a supported concurrent activation API. Missing/unreadable enrollment or company state refuses contextual effects. Genuine source-free standalone mail keeps its normal approval behavior; it never serves as an exemption for a bound reply.

Company joins must preserve this authority latch without unnecessarily disabling existing history-free joins. Existing assignment-state/history/schema refusals remain unchanged. A join with no assignment history must retain the stricter source/destination enrollment in the destination, bound to its actual immutable space, inside the existing source/destination write transactions; managed cannot become never-enabled, and legacy-unknown cannot become never-enabled merely by joining. Preserve classification provenance in the existing join audit and refuse before cutover if it cannot be retained. Destination membership still requires independent trusted provisioning; a memory key or join cannot forge assignment membership. Verify history-free managed-to-managed and never-enabled joins plus downgrade refusal/rollback; no lossless assignment-history migration or live join belongs to this task. Rollback retains enrollment and assignment tables; older binaries cannot activate authority or join managed stores safely.

## Scope and decisions

1. Check the durable enrollment classification before applying managed assignment authority; never-enabled contextual effects use the serialized compatibility path without root trust. Factor reusable reply admission and a bounded company-serialized effect guard from the current scoped draft policy. Resolve exact root and source from authoritative owner-scoped stored mail and validated RFC reply headers. All supplied identifiers (root, In-Reply-To, References, original source/task context) must agree; malformed, foreign-owner, mismatched or unavailable source refuses the contextual operation. Require exact source target in current accepted inbound coverage. Existing scoped draft behavior remains at least as strict.
2. Apply the guard to every reply-bearing draft create/update and actual email transport handoff, independent of whether chat negotiated the old opt-in flag. Bind existing draft identity at send, so assignment after composition prevents sending; retries and direct slash/solve sends receive the same enforcement. Approval edits cannot strip/change threading to escape the decision.
3. Collect provider/source evidence before the company lock. Re-admit current verified identity, membership, store binding and assignment row under its writer lock; serialize the private write or bounded final provider transport handoff with assignment mutation. Retain the transport lock through the irreversible provider acceptance point, with existing bounded transport timeout and truthful uncertain-delivery handling; avoid model calls, IMAP evidence scans or unrelated work inside it. No proof from a check immediately before an unlocked send. Retain existing single-send draft claims and exact sent/uncertain bookkeeping.
4. Carry explicit reply source/thread binding through kernel contextual compose/send and task-conversation entry points. Negotiation must fail closed against an engine lacking the strengthened policy. Generic operator chat that performs contextual email work cannot silently omit its known source binding. A restrictive origin/scope may constrain effects, but no caller-supplied flag may relax assignment checks or claim human authority. Identify the MrCall custom send launcher's required explicit binding; clone-specific content remains outside shared kernel code.
5. A source-free standalone email has no reply headers or known bound task/source context and retains its existing compose/send approval behavior. A caller cannot turn an already bound reply draft/turn into standalone by dropping metadata. Arbitrary text pretending to be a new email is not semantically classified as a reply; state that limit accurately. Fixed-template kernel campaign first-contact/bulk delivery outside contextual engine replies is unchanged.
6. Active assignments, pending candidates, closed coverage and incomplete/conflicting identity remain held. Fresh later-inbound after close is admitted only for the newly uncovered actual inbound identity; closed older targets remain blocked. Unrelated exact threads from the same sender remain independently usable.

## Acceptance

- An ambiguous local legacy store is held until the documented offline trusted-data-owner classification or privileged enrollment; ordinary chat/raw RPC cannot perform it. Managed/history-bearing stores cannot be downgraded by that procedure, and hosted tenant authority cannot classify a hosted store. Classification retains its actual explicit historical-attestation provenance.
- Fresh local never-enabled company and genuine pre-assignment upgrade can create, update and send ordinary contextual replies without privileged host files. Migration evidence is collected before additive schema creation and persists across interrupted upgrade/restart. Missing/unreadable enrollment, partial schemas and ambiguous assignment-capable legacy stores refuse.
- Empty but managed companies with missing/revoked/malformed trust refuse create/update/send; retained task/event/receipt history cannot become unmanaged when trust disappears. Existing valid-trust empty companies migrate managed, and no caller flag or raw RPC can reset enrollment. Joined stores cannot downgrade the latch.
- A real two-connection enrollment-versus-provider-handoff race demonstrates either unmanaged delivery before enrollment or managed admission after enrollment, never activation between the compatibility check and irreversible delivery. Failed provisioning retains managed/blocked state.
- A regression using real private/company SQLite fixtures demonstrates the old unscoped reply create succeeds on an assigned thread and the repaired implementation refuses before any row mutation. Missing trust, unknown/partial provider scope and conflicting source all fail closed.
- Real generic chat dispatch to actual create/update/send tool paths cannot bypass the guard via omitted old scope, allow send_draft approval, forged identity, changed threading, stripped binding or reused pre-assignment drafts. No paid model dispatch or customer delivery in tests; deterministic test agents and provider doubles preserve actual write/dispatch boundaries.
- Cover create, update and send; direct `/email send`, solve send, IMAP send/send_message and guarded legacy task-orchestrator entry points. Test actual enabled transports, mark absent OAuth integrations explicitly unavailable.
- Two connections/threads prove competing assignment cannot commit between final admission and draft insert/provider handoff. The opposite order (assignment wins first) yields zero transport calls. Failed or uncertain transport retains the existing nonduplicating claim semantics, never reopens delivered mail.
- Normal exact-source reply succeeds; unrelated same-sender thread and genuinely source-free standalone composition succeed. Known task/source context cannot become standalone by dropping tool headers. Later-inbound target coverage, owner isolation and revoked membership are verified.
- Existing scoped draft, request-readonly, approval, draft idempotence, double-send, ordinary task/Qonto and kernel CLI/transport regression suites pass. Strengthened capability negotiation is covered with current and older fake engines.
- Fresh milestone integration, documentation critic and final review verify exact code and raw logs. No live sends, assignment mutation, host keys, store joins, tag/push/release, clone pin changes or paid operator ticks.

## Constraints and rollback

No self-approved bypass flag or enrollment downgrade, no independent new assignment ledger, no company-specific kernel branch, no broad source/refactor cleanup. Respect the shared-kernel anti-fork charter and existing bounded modules. Rollback only owned source hunks; retain all assignment records/audit and existing draft history. Reverting restores the known previous generic-chat gap and must not be described as assignment-safe. Production enablement requires separate authorization after local acceptance.
